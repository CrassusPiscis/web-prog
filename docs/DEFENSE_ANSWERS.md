# Короткие ответы на 20 вопросов лабораторной №4

1. **React, Vue, Angular, Svelte.** React — библиотека компонентов, окружение выбираем отдельно. Vue предоставляет реактивность и шаблоны. Angular — более полный фреймворк с DI и набором встроенных средств. Svelte переносит значительную часть работы в компиляцию. Наш вариант — React с Vite, маршруты через React Router.

2. **SPA и маршрутизация.** Браузер загружает HTML-оболочку, затем JavaScript меняет компоненты без полной перезагрузки. BrowserRouter связывает адрес с компонентом, Link выполняет переход. Для прямого открытия вложенного адреса Nginx возвращает index.html.

3. **Компоненты и props.** Компонент описывает часть интерфейса. StudentsPage передаёт StudentTable массив students, признак admin и callback onDelete. Дочерний компонент не меняет props: он вызывает callback, а родитель изменяет данные или повторяет запрос.

4. **Жизненный цикл и hooks.** useState хранит состояние, useEffect синхронизирует компонент с внешней системой после render, useRef хранит изменяемое значение без повторного render. В useStudents эффект создаёт подписку, cleanup её отменяет. В StrictMode разработка дополнительно проверяет корректность очистки.

5. **Рендеринг, Virtual DOM, reconciliation.** React вычисляет описание интерфейса и сопоставляет новое дерево с предыдущим, затем применяет необходимые изменения DOM. key помогает сопоставлять элементы списка; используем id, а не индекс строки. Условный рендеринг выбирает загрузку, ошибку, пустой список или таблицу.

6. **Реактивность интерфейса.** setState планирует новое отображение с обновлёнными данными. Прямой students.push не сообщает React об изменении состояния. Для обновления массивов и объектов создаём новые значения. React-состояние и потоки RxJS решают разные задачи.

7. **Локальное и глобальное состояние.** Поля формы и saving локальны конкретной странице. Пользователь и вход/выход нужны нескольким страницам, поэтому находятся в AuthContext. Не складываем в глобальное состояние всё подряд. Доступ к контексту — через useAuth.

8. **Реактивное программирование.** Описываем преобразования потока событий: новые параметры → пауза ввода → последний запрос → состояние результата. Императивный код отдельно управляет каждым событием и отменой; RxJS позволяет выразить эти связи операторами.

9. **Observable, Observer, Subject, BehaviorSubject, Subscription.** Observable описывает источник значений. Observer получает next/error/complete. Subject одновременно принимает и рассылает события. BehaviorSubject хранит текущее значение и отдаёт его новому подписчику. Subscription позволяет отменить подписку. В нашем проекте параметры находятся в BehaviorSubject.

10. **Операторы.** map преобразует значение; distinctUntilChanged отбрасывает повторы; switchMap переключается на последний внутренний поток; catchError обрабатывает ошибку; startWith выдаёт начальное состояние; shareReplay делит последний результат. timer реализует ожидание ввода. Важно: catchError стоит внутри обработки одного запроса, поэтому ошибка не убивает весь поиск.

11. **Hot/cold и утечки.** Cold Observable обычно запускает собственную работу при подписке; обёртка HTTP в нашем проекте создаёт новый fetch. Subject — hot-источник, события доступны текущим подписчикам. При уходе со страницы вызываем unsubscribe; он отменяет fetch через AbortController. shareReplay с refCount освобождает upstream без подписчиков.

12. **Поиск и устаревшие запросы.** При новом вводе switchMap немедленно отменяет предыдущую операцию и ждёт паузу перед следующей. Отмена подписки вызывает abort. Поздний ответ не должен перезаписать свежий. Просто использовать from(fetch()) недостаточно для физической отмены сетевой работы.

13. **Валидация и ошибки.** Проверяем поля до отправки, но backend повторяет свои проверки. Показываем ошибки рядом с полями и общий ответ API. saving отключает форму; ref-lock защищает от повторного события до следующего render. Отдельно обрабатываем 400/401/403/404/409/500 и отсутствие связи.

14. **JWT и вход.** Пароль проверяет сервер через BCrypt. Access используется для запросов, refresh — для обновления токенов. Подпись JWT обеспечивает проверку целостности, содержимое не зашифровано. На 401 защищённого запроса client выполняет один общий refresh и один повтор. Проверка логина не запускает refresh.

15. **Роли и маршруты.** ProtectedRoute проверяет готовность сессии и пользователя; admin-вариант дополнительно проверяет роль. Это удобство интерфейса. Настоящий запрет POST/PUT/PATCH/DELETE для USER задаётся SecurityConfig на сервере. Роль фильтр перечитывает из БД, поэтому старый ADMIN-токен после снятия роли не сохраняет права.

16. **XSS и CSRF.** React экранирует обычные текстовые значения; не используем dangerouslySetInnerHTML с данными пользователей. Токены в sessionStorage доступны JavaScript, поэтому защита от XSS существенна. В нашей схеме Bearer браузер не прикладывает автоматически как cookie. При переходе на cookie-аутентификацию нужно заново спроектировать CSRF-защиту. Секрет подписи JWT остаётся на backend.

17. **Архитектура.** pages собирают экраны, components отображают части UI, api знает HTTP, auth хранит сессию, reactive управляет потоками, hooks связывают их с React. Не смешиваем SQL, HTTP и разметку в одном компоненте. Для backend сохраняется Controller → Service → Repository.

18. **Docker.** Dockerfile — рецепт сборки образа. Образ — подготовленная файловая система и настройки запуска. Контейнер — работающий экземпляр образа. Volume хранит данные PostgreSQL отдельно от жизни контейнера.

19. **Multi-stage.** В первом этапе Node выполняет npm ci и npm run build. Второй этап Nginx получает только dist и nginx.conf. В production не нужен сервер разработки Vite, исходники и node_modules. API проксируется отдельно от SPA-маршрутов.

20. **Compose и окружение.** Compose запускает frontend/backend/postgres в общей сети. Backend обращается к postgres:5432, Nginx — к backend:8000. localhost внутри контейнера указывает на этот контейнер. .env участвует в подстановке Compose, environment передаёт настройки процессу Java. Vite proxy используется только в разработке. JWT_SECRET не попадает в frontend.

## Что честно назвать ограничениями

- Выход очищает браузерную сессию, но серверный отзыв refresh-токенов не добавлен.
- Профиль и роль актуальны по серверу; UI может узнать о смене роли после обновления профиля или первого 403.
- Чтение COUNT и списка без отдельной изоляции снимка не гарантирует их совпадение при одновременных изменениях базы.
- Валидация клиента помогает пользователю; целостность обеспечивает backend и ограничения PostgreSQL.
